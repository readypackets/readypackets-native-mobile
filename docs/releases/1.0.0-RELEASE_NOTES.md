# ReadyPackets Native Mobile 1.0.0 — Release Notes

**Release status:** Internal / staging candidate. **Publication decision:** Pending signed-device verification, store metadata review, and production Portal release approval.

## Release summary

ReadyPackets Native Mobile 1.0.0 introduces two independent native customer applications: a SwiftUI client for iOS and a Kotlin/Jetpack Compose client for Android. Both applications use the self-hosted ReadyPackets mobile API and browser-hosted OAuth 2.1 with PKCE. The release is designed for authenticated customers who need to review authorized work, place packet requests, follow order progress, manage their signed-in device, and request account deletion without embedding a browser shell or payment form.

| Release area | Included in 1.0.0 | Authority and boundary |
|---|---|---|
| Secure access | System-browser OAuth 2.1 + PKCE, short-lived access tokens, rotated refresh-token families, biometric re-entry | The Portal owns authentication, MFA, token rotation, device revocation, and account status. |
| Customer workspace | Dashboard, authorized orders, order detail, profile, device list, logout, deletion request | The Portal authorizes every object and action. |
| Packet ordering | Listed packet catalog, one selected packet tier per group, optional project name, idempotent submission | The Portal resolves listed SKUs, quote, price, payment state, audit record, workflow, and next action. |
| Payment and quote handling | A secure Portal handoff instruction or quote-required status | Neither application collects card data, completes payment, or activates work locally. |
| Platform safety | Keychain / Keystore protection, biometric gate, Universal Links / Android App Links | Each client uses native platform security services; no cross-platform runtime or web wrapper is included. |

## What is new

The customer can open **Orders**, select **Place order**, choose currently listed packet options, and record a request. The mobile API accepts only public packet SKUs, a bounded quantity, and an optional project name. It rejects client-provided prices, payment states, internal product identifiers, and workflow states. Repeated submissions are protected by an idempotency key. A normal request returns a Portal-managed payment action; a custom-priced request returns an awaiting-quote action.

The source package also includes the permanent self-hosted mobile-experience demonstration website under `website/mobile-experience-preview/`. That site uses representative local data only and is not a live customer ordering surface.

## Known release boundaries

The release does not provide native card entry, refunds, staff or administrator controls, bulk export, platform configuration, backup/restore, or privileged Portal administration. Push registration, optional diagnostics, uploads, messages, and audio must be disclosed only when their corresponding production features are enabled. The release owner must not claim feature availability or privacy practices that differ from the submitted binary and deployed Portal configuration.

## Recommended release sequence

Promote the Portal API to staging first, configure the iOS Universal Link and Android App Link domains, then distribute Android through Play Internal Testing and iOS through TestFlight. TestFlight supports beta distribution, tester management, feedback, and up to 90 days of build availability; internal testing is limited to eligible App Store Connect users. [1] Google Play recommends an internal test before broader testing and supports internal cohorts of up to 100 testers. [2]
